L'installation

Brancher le harness, puis créer un projet.

L'installation se fait une fois par machine. Elle ne copie rien : elle pose des liens vers vos deux dépôts. Ensuite, chaque nouveau projet part d'un gabarit qui contient déjà la méthode.

Ouvrir le dépôt sur GitHub Récupérer le moteur
Avant de commencer

Ce qu'il faut sur le PC.

les outils

Git, gh, Node et un agent

git, la commande GitHub gh, Node 24 avec npm, et au moins un agent : Claude Code ou OpenCode. Les deux peuvent cohabiter, ils liront les mêmes règles.

votre instance

Un dépôt privé avec config/

Copiez harness.conf.exemple du moteur en config/harness.conf et remplissez-le. Ajoutez profil.md (votre façon de travailler) et interdits.txt (la liste noire). profils.md est facultatif.

Récupérer le moteur

Un clone, à côté de votre instance.

Cloner veut dire copier le dépôt GitHub sur votre PC, avec tout son historique. Rangez le moteur et votre instance dans le même dossier parent : les chemins restent courts.

git clone git@github.com:mPelerin/harness.git
cd harness

Si le dépôt est privé, son propriétaire doit d'abord vous en donner l'accès. Pour suivre les nouveautés plus tard : git pull dans ce dossier, puis relancez l'installeur et le vérificateur.

Voir le dépôt sur GitHub
Trois commandes

Essayer, installer, vérifier.

Depuis le dossier du moteur. Remplacez le chemin par celui de votre instance.

bash scripts/installer.sh --essai --config <votre-instance>/config
bash scripts/installer.sh --config <votre-instance>/config
bash scripts/verifier-install.sh

  1. L'essai à blanc

    Il montre ce qui serait fait, sans rien changer. Lisez-le avant de lancer la vraie installation.

  2. L'installation

    Elle pose les liens et génère les règles. Elle ne supprime jamais rien : ce qui gêne est mis de côté dans un dossier daté.

  3. Le vérificateur

    Il contrôle tout en lecture seule et finit par OK ou STOP. Une installation conforme affiche zéro problème.

Ce que fait l'installeur

Des liens, pas des copies.

Un lien symbolique est un raccourci vers un fichier ou un dossier. Si vous modifiez l'original, tous les agents voient le changement, sans rien recopier.

Sur le PCPointe versPour
~/.config/harnessle dossier config/ de votre instanceque les skills lisent vos valeurs
~/.claude/CLAUDE.mdles règles généréesClaude Code
~/.config/opencode/AGENTS.mdles mêmes règles généréesOpenCode
~/.claude/skills/<nom>chaque skill du moteur, puis de l'instanceles deux agents
~/.local/bin/nouveau-projet, orchestrateur, pre-volles commandes du harness

Les règles sont générées : le AGENTS.md du moteur, puis votre profil.md à la suite. Après un changement de l'un des deux, relancez l'installeur. Le vérificateur signale des règles qui ne sont plus à jour.

Prouver que c'est lu

Deux mots de contrôle.

Ouvrez une session neuve et posez ces deux questions. Une mauvaise réponse veut dire que l'agent ne lit pas le harness.

Démarrer un projet

Du classeur au premier ticket technique

  1. Ouvrir le classeur

    Depuis le coffre Projets, ouvrez une session d’agent et demandez-lui de lancer le skill projet. Il crée les notes à partir des modèles. Dans Obsidian, ouvrez la note principale du projet.

  2. Commencer le cadrage

    Dites "cadrage". L’agent pose les questions et rédige les notes. Au premier entretien, il peut préparer GitHub avec votre accord.

  3. Créer le socle au bon moment

    Après validation du cadrage et autorisation du ticket socle, l’agent installe la technologie choisie dans code/ et met en place les tests automatiques.

La commande nouveau-projet reste le raccourci du gabarit Next.js. Le parcours par le coffre laisse le choix de la technologie au cadrage.

Voir le fonctionnement du coffre
Gabarit Next.js

Une commande, cinq étapes.

Ce raccourci installe le profil Next.js. Le nom s’écrit en minuscules, avec des chiffres ou des tirets.

nouveau-projet mon-appli
  1. 1 sur 5

    Créer l'appli Next.js

    Avec le générateur officiel, à une version fixée.

  2. 2 sur 5

    Poser le socle et le profil

    Le gabarit commun, le profil TypeScript et Next.js, et les fichiers des outils MCP pour les deux agents.

  3. 3 sur 5

    Installer les outils de contrôle

    Prettier (mise en forme), Vitest (tests) et Lefthook (hooks Git), chacun à une version fixée.

  4. 4 sur 5

    Fixer les versions et faire le premier commit

    Chaque plage de version comme ^5 est remplacée par la version réellement installée. Les hooks sont activés.

  5. 5 sur 5

    Lancer la vérification complète

    Le projet finit par OK. Le gabarit est prêt à être vérifié dans votre environnement.

Relier à GitHub

main d'abord, preprod ensuite.

GitHub prend la première branche poussée comme branche par défaut. Elle doit toujours être main, jamais preprod.

git remote add origin git@github.com:<compte>/mon-appli.git
git push -u origin main
git switch -c preprod && git push -u origin preprod
gh repo view <compte>/mon-appli --json defaultBranchRef

La dernière commande doit afficher main. Sinon : gh repo edit <compte>/mon-appli --default-branch main.

Revenir en arrière

Tout se défait.

L'installeur ne fait que des liens et un fichier généré. Retirer un lien ne touche pas au fichier visé.

  • Enlever un skill : unlink ~/.claude/skills/<nom>
  • Retirer les règles : unlink ~/.claude/CLAUDE.md et unlink ~/.config/opencode/AGENTS.md, puis remettre l'ancien fichier depuis la sauvegarde.
  • Retrouver ce qui a été mis de côté : le dossier daté de DOSSIER_SAUVEGARDES, sinon ~/.local/state/harness/sauvegardes/, avec l'arborescence d'origine.
Ajouter un skill

Quatre gestes.

  1. Lire le format

    docs/skills.md du moteur. Le modèle à copier est skills/test-harness/SKILL.md.

  2. Choisir le bon dépôt

    Un skill pour tout le monde va dans le moteur, un skill personnel dans votre instance. Un même nom dans les deux est refusé.

  3. Relancer l'installeur, puis le vérificateur

    Le nouveau lien est posé et contrôlé.

  4. Fermer puis rouvrir les agents

    Les skills se lisent au démarrage d'une session.
