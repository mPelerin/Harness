La méthode

De l'idée en ligne, sans sauter d'étape.

La méthode tient en une suite de skills. Chacun fait une chose, la prouve, puis passe la main au suivant. Entre eux, trois portes où rien n'avance sans vous.

Le circuit

Six étapes, trois portes.

Les points pleins sont les portes. Une porte est un point d'arrêt : l'agent prépare, propose et prouve, puis il attend votre "go" écrit.

  1. cadrage

    Transformer l'idée en documents

    L'agent reformule, puis pose ses questions une à la fois. Il écrit docs/cadrage/ : le PRD (ce que fait le produit, pour qui, ce qui est hors périmètre), les écrans et les user stories. Il remplit le AGENTS.md du projet et commite sur preprod.

  2. Porte 1 : décider

    Vous relisez, vous dites "go"

    Tant que le cadrage n'est pas validé, aucune ligne de code n'est écrite.

  3. tickets

    Découper en tickets fins

    Chaque story devient un ou plusieurs tickets GitHub qui traversent toute l'appli, de l'écran à la base. Chacun dit ce qui est fini, ce qui est hors périmètre et ce qu'il faut préparer avant de coder.

  4. feature

    Coder le lot, ticket après ticket

    Pour chaque ticket : une branche, le code en partant des tests, la vérification, la relecture, la fiche QA, puis la demande de fusion jusqu'à la CI verte. Les questions qui restent arrivent en un seul message, au début.

  5. Porte 2 : tester

    Un seul tableau pour tout le lot

    Vous testez à l'écran avec la fiche QA, puis vous dites "go tout" ou "go 2 4". L'agent fusionne chaque ticket dans preprod et le ferme à la main.

  6. Porte 3 : mettre en ligne

    Fusionner preprod sur main

    Votre "go mise en ligne", et rien d'autre. L'agent prouve ensuite que la bonne version est en ligne, pas seulement que le site répond.

Les trois portes

Chaque porte a sa raison.

Elles viennent d'erreurs réelles. Une case que vous ne pouvez pas cocher veut dire "on n'ouvre pas encore". La liste complète est dans docs/portes.md de chaque projet.

Porte 1

Décider, avant le code

Le ticket dit ce qu'on fait et ce qu'on ne fait pas. Ses critères de fin sont des phrases que vous pouvez vérifier vous-même. Les tests ne savent pas ce que "fini" veut dire pour vous.

Porte 2

Tester, avant la fusion

Une CI verte n'est pas un "oui". On a déjà vu plus de 2 000 tests verts autour d'une fonction qui n'avait jamais tourné, parce que les tests imitaient la base.

Porte 3

Mettre en ligne

Le code se déploie tout seul, la base de données non. Avant le "go" : le changement de base est appliqué, la commande de retour arrière est écrite, et vous pouvez surveiller ensuite.

Un travail plus propre

Les habitudes qui font la différence.

Elles sont écrites dans les règles communes et dans les skills. L'agent les suit sans qu'on les lui rappelle.

  1. Une modification à la fois

    Chaque changement est testé avant le suivant. Quand quelque chose casse, on sait tout de suite lequel.

  2. Pas de "ça marche" sans preuve

    La preuve, c'est la commande lancée et sa sortie, liées à un commit précis. Par exemple npm run verifier, code 0, commit a1b2c3d.

  3. Le vérifié, l'hypothèse et la recommandation, séparés

    Vous savez toujours ce qui a été contrôlé et ce qui n'est qu'une supposition de l'agent.

  4. Lire avant de demander

    L'agent lit le AGENTS.md du projet, le README et docs/ avant de poser une question. Une réponse qui resservira y est notée, pour ne jamais vous la redemander.

  5. Un ticket, un commit, une fusion en squash

    Le squash réunit tout le travail d'une branche en un seul commit au moment de la fusion. L'historique se lit comme une liste de tickets.

  6. Le test d'abord

    Le skill tdd écrit un test, le voit échouer, puis écrit le plus petit code qui le fait passer. Pour un bug, il reproduit d'abord le défaut par un test.

  7. Une relecture par angles

    Le skill revue passe un angle à la fois et classe chaque problème avec son fichier:ligne. Quand le changement touche à l'argent, aux droits d'accès, aux données personnelles ou à la base, un autre modèle relit.

  8. Une fiche QA qui ne vous laisse que l'écran

    L'agent prouve tout ce qu'une commande peut prouver. Il vous laisse huit étapes à l'écran au plus, dont au moins un chemin qui doit échouer, comme une mauvaise saisie ou un double clic.

  9. Les prérequis humains déclarés

    Une variable, un compte ou une migration à poser avant de coder est écrit dans le ticket. La commande pre-vol les liste et bloque le lot s'il en manque.

  10. Des numéros lus, jamais supposés

    Les tickets et les demandes de fusion partagent la même numérotation sur GitHub. L'agent lit le numéro dans la sortie de la commande, il ne le devine pas.

  11. Un retour arrière pour chaque action

    Ce qui change votre PC ou un dépôt est noté avec la commande qui le défait.

  12. Une courte recherche avant de répondre

    Dès que le sujet touche un outil, un marché ou une règle, l'agent cherche ce qui existe, ce qui se fait et ce qui n'est pas possible. Il cite ses sources avec leurs dates.

  13. Les idées au parking

    Une idée nouvelle en cours de route ne détourne pas le travail. Elle est notée, et vous décidez si on la lance.

Les skills

Treize fiches de travail.

Un skill est un dossier avec un fichier SKILL.md. Sa description dit ce qu'il fait et quand l'utiliser : c'est elle qui le déclenche.

cadrage

De l'idée aux documents validés : PRD, écrans, stories, AGENTS.md du projet.

tickets

Crée, relit et corrige les tickets GitHub, à partir des stories ou pour un bug isolé.

feature

Réalise un lot de tickets d'affilée et s'arrête une fois, à la porte 2.

tdd

Un comportement à la fois, en partant d'un test qui échoue.

verifier

Lance les contrôles du projet et rend la preuve : commande, code de sortie, dernière ligne, commit.

revue

Relit un changement sous plusieurs angles séparés et classe les problèmes.

qa-prep

Prépare la fiche de test et la bloque si un prérequis humain manque.

livrer

Pousse, ouvre la demande de fusion, attend la CI, fusionne après votre "go".

retro

Transforme une erreur en garde-fou : un contrôle automatique d'abord, une règle écrite sinon.

cloture-session

Écrit la passation en fin de session, ou repart de la dernière en reprise.

nuit

Confie le lot à Hermès sur le serveur. Le matin, la préprod est prête à tester.

preprod

Déploie la branche preprod derrière un login, puis prouve que la bonne version tourne.

test-harness

Le skill témoin : il prouve que les skills sont bien installés et lus.

Ce que l'agent ne fait jamais seul

Certaines actions attendent votre "go".

  • Commencer un ticket sensible (argent, droits d'accès, données personnelles, base de données, nouvelle bibliothèque) sans un "go" de plus.
  • Fusionner dans preprod sans votre "go" de porte 2 et une CI toute verte.
  • Fusionner sur main sans votre "go" de porte 3.
  • Changer la base de données en ligne sans un "go" écrit à part.
  • Ajouter une bibliothèque avant de vous avoir montré son origine et sa version exacte.
  • Pousser en force, commiter directement sur main ou contourner un hook : jamais, même avec un "go".
Quel modèle choisir

Le bon modèle pour la tâche.

Deux questions suffisent. Une erreur serait-elle coûteuse à défaire ? La tâche demande-t-elle beaucoup de réflexion ? Deux oui : le plus puissant. Un seul : le milieu. Aucun : le plus léger.

deux oui

Le plus puissant

Un script qui modifie votre système, la conception d'un skill ou d'une architecture, une décision difficile à défaire.

un oui

Le milieu de gamme

Un script de contrôle, un gabarit, une configuration, une revue de code. Soigné, mais facile à vérifier ensuite.

aucun

Le plus léger

Guider une commande, lire une sortie, rédiger un README ou un récapitulatif. Peu de réflexion, beaucoup d'échanges.

L'agent termine ses messages par le modèle conseillé pour l'action suivante. Il ne change pas de modèle lui-même : c'est vous qui le faites dans l'appli.
